# 실시간 아레나 배틀 전투 규칙 밸런스 최종 분석 요청서

- 문서 상태: 서버 아키텍처·상태 계약 확정, 전투 밸런스 검증 대기
- 작성일: 2026-07-30
- 대상 기능: Firebase 로그인 사용자 간 1대1 동시 선택형 실시간 아레나
- 이번 단계: 분석과 추천만 수행
- 구현 여부: 구현 금지

> 이 문서는 이전 실시간 아레나 분석 요청과 보강 문장을 모두 대체하는 독립 실행 지시서다. 이전 문서와 충돌하면 이 문서를 우선한다.

---

## 1. 요청 목적

실시간 아레나 배틀의 서버 아키텍처와 상태 계약은 이미 확정됐다.

이번 요청의 목적은 아키텍처를 다시 설계하는 것이 아니라, 실제 저장소 코드와 허용된 로컬 데이터를 사용해 아래 다섯 가지 전투 규칙만 비교·검증하고 최종 추천값을 정하는 것이다.

1. 공격 대 특수공격의 약화 피해
2. 특수공격 기본 보너스
3. 성장 단계별 HP·`baseAttack` 후보
4. `powerGapUnit`
5. 동일 단계 매칭 범위

중요:

> 지금은 구현 단계가 아니다. 프로덕션 코드, 테스트, 설정, Rules, 인덱스, 데이터는 수정하지 않는다.

## 2. 이번 분석의 범위

### 2.1 반드시 분석할 항목

다음 다섯 항목만 수치와 전략 관점에서 비교한다.

```text
1. 공격 vs 특수공격 약화 피해
2. 특수공격 기본 보너스
3. 성장 단계별 HP·baseAttack
4. powerGapUnit
5. 동일 단계 매칭 범위
```

각 항목은 다음 형식으로 결론을 작성한다.

```text
후보별 수치 결과
→ 장점
→ 문제점
→ 추천안
→ 추천 이유
→ 아직 확인할 수 없는 한계
```

### 2.2 이번 분석에서 다시 논의하지 않을 항목

아래 내용은 확정된 서버 계약이다. 새로운 아키텍처 대안이나 다른 정본 DB를 제안하지 않는다.

- Firebase Auth 유지
- Firestore를 진행 중 배틀의 유일한 정본으로 사용
- 기존 Vercel API에서 서버 권위 판정
- 기존 `arena-v2` 라우터 operation 재사용 우선
- 미공개 행동은 서버 전용 secret 상태에 저장
- 참가자 공개 문서는 실제 공개 상태가 바뀔 때만 갱신
- Supabase는 선택적 비동기 archive·통계 저장소
- Ably는 MVP 정본·판정 경로에서 제외
- 배틀 중 원본 슬롯 HP·스탯을 쓰지 않음
- 별도 상시 WebSocket 서버나 라운드별 서버 타이머를 추가하지 않음

확정 계약에서 실제 코드와 충돌하는 사실이 발견되면 대체 아키텍처를 설계하지 말고 다음 형식으로만 보고한다.

```text
충돌 위치
→ 현재 코드 근거
→ 확정 계약에 미치는 영향
→ 구현 전에 필요한 최소 조정
```

## 3. 데이터 접근 경계

운영 Firebase, Supabase, Ably 데이터에는 접근하지 않는다.

분석에 사용할 수 있는 자료는 다음뿐이다.

- 저장소 안의 정적 디지몬 데이터
- 기존 테스트 fixture
- Firebase Emulator에 이미 준비된 테스트 데이터
- 사용자가 직접 제공한 익명화 export
- 기존 `calculatePower()` 코드에서 도출한 이론적 범위

금지 사항:

- Firebase Admin 자격증명을 찾아 운영 Firestore 읽기
- 운영 Supabase 테이블 조회
- 운영 Ably 채널 연결 또는 메시지 발행
- 임의로 만든 슬롯을 실제 사용자 표본처럼 보고
- 이론 시나리오를 실측 분포라고 표현

실제 육성 슬롯 표본이 없다면 다음을 명시한다.

```text
실제 슬롯 power 분포는 확인하지 못했다.
아래 결과는 정적 데이터와 calculatePower() 코드상 이론 범위에 기반한다.
```

정적 데이터, 테스트 fixture, 이론 시나리오, 익명화 실측 표본의 결과는 표와 설명에서 서로 구분한다.

## 4. 용어와 코드 키

### 4.1 행동 이름

UI 행동 이름은 다음으로 고정한다.

```text
공격
방어
특수공격
```

권장 내부 값은 다음과 같다.

```js
"attack"
"guard"
"special_attack"
```

`필살기`라는 명칭은 사용하지 않는다. 세 번째 행동의 핵심은 고정 고화력이나 전투당 1회 기술이 아니라 방어 관통이다.

### 4.2 성장 단계 키

분석과 코드 예시에는 저장소의 실제 성장 단계 키를 사용한다.

| UI 명칭 | 코드 키 |
|---|---|
| 성장기 | `Child` |
| 성숙기 | `Adult` |
| 완전체 | `Perfect` |
| 궁극체 | `Ultimate` |
| 초궁극체 | `Super Ultimate` |

`rookie`, `champion`, `mega`, `ultra` 같은 별도 별칭을 새 규칙의 정본 키로 만들지 않는다.

유년기 I·II는 이번 경쟁형 밸런스의 기본 모집단에서 제외한다. 필요하면 제외 근거와 데이터 특성만 보고한다.

## 5. 확정된 서버 계약

이 절은 검토 후보가 아니라 분석이 따라야 하는 전제다.

### 5.1 정본과 서비스 역할

```text
Firebase Auth
→ 사용자 인증

Vercel arena-v2 API
→ 참가자 검증
→ 슬롯 스냅샷 생성
→ 행동 제출
→ timeout 판정
→ 라운드 resolve

Firestore
→ 진행 중 배틀과 최종 결과의 정본

Supabase
→ 선택적 종료 기록·통계 archive

Ably
→ MVP 판정·상태 정본 경로에서 제외
```

Supabase archive 실패는 배틀 판정이나 종료를 막지 않는다. Firestore와 Supabase에 현재 HP나 현재 라운드를 동시에 정본으로 저장하지 않는다.

Ably를 사용하더라도 향후 측정 결과가 필요성을 증명한 뒤 Firestore commit 이후 알림·presence 용도로만 검토한다. 이번 분석에서는 Ably 대안을 다시 제안하지 않는다.

### 5.2 공개 상태와 secret 상태

참가자가 구독하는 공개 정본:

```text
realtimeArenaBattles/{battleId}
```

서버만 읽고 쓰는 secret 정본:

```text
realtimeArenaBattleSecrets/{battleId}
```

첫 번째 행동 제출 시에는 secret 상태만 갱신한다.

참가자 공개 문서의 다음 값은 변경하지 않는다.

```text
updatedAt
stateVersion
status
round
deadlineAt
```

공개 문서는 다음 경우에만 갱신한다.

- 양쪽 행동이 모여 라운드가 resolve됨
- timeout으로 현재 라운드가 resolve됨
- 준비·시작·포기·종료처럼 실제 공개 상태가 전환됨

공개 문서에 다음 값을 저장하거나 노출하지 않는다.

```js
hostSubmitted
guestSubmitted
submittedCount
opponentHasSubmitted
상대 action
상대 action 제출 시각
```

행동 내용뿐 아니라 첫 제출이 있었다는 사실도 공개 문서 변화로 추론할 수 없어야 한다.

### 5.3 viewer 전용 상태 복구

새로고침·재접속 시 자신의 제출 여부는 공개 Firestore 문서에서 읽지 않는다.

인증된 상태 복구 API가 secret 상태에서 호출자 UID에 해당하는 정보만 읽어 응답 시 viewer projection을 계산한다.

예시:

```js
{
  battle: {
    status: "selecting",
    round: 3,
    deadlineAt: "...",
    stateVersion: 7
  },
  viewer: {
    hasSubmitted: true
  }
}
```

반환 금지 예시:

```js
{
  opponentHasSubmitted: false,
  submittedCount: 1
}
```

`viewer.hasSubmitted`는 공개 문서에 영구 저장된 필드가 아니다. 서버가 호출자별로 계산해 반환하는 viewer 전용 projection이다.

viewer 전용 상태 복구 응답에는 다음 헤더를 적용한다.

```http
Cache-Control: private, no-store
```

CDN 또는 공유 캐시를 통해 다른 사용자에게 재사용되지 않아야 한다.

### 5.4 로그 비공개 계약

행동 제출 API와 상태 복구 API는 다음 정보를 서버 로그, 오류 로그, 분석 이벤트에 기록하지 않는다.

- `action`
- 양쪽 제출 상태
- secret 문서 원문
- viewer projection의 민감 필드
- 행동 제출 시각을 통해 상대 선택을 추론할 수 있는 세부 정보

오류 로그에는 운영 진단에 필요한 최소 정보만 남긴다.

```text
battleId
round
errorCode
stateVersion
```

### 5.5 라운드 판정과 멱등성

라운드 판정의 고유 단위는 다음이다.

```text
battleId + round
```

멱등성은 같은 요청이 재시도돼도 피해나 상태 전환이 한 번만 적용되는 성질을 뜻한다. 구현 의미는 다음과 같이 고정한다.

```text
해당 battleId + round의 committed state transition은 최대 한 번만 발생한다.
하나의 resolve가 commit된 뒤 모든 재시도와 경합 요청은 저장된 동일 결과를 반환한다.
따라서 성공적으로 resolve된 라운드의 논리 결과는 정확히 하나다.
```

다음이 보장돼야 한다.

- 같은 `requestId`의 행동 재전송은 저장된 동일 결과 반환
- 같은 라운드에 다른 행동으로 변경 제출 금지
- 두 행동이 동시에 제출돼도 라운드 판정 1회
- 양쪽이 서로 다른 `requestId`로 timeout resolve를 동시에 호출해도 판정 1회
- 이미 판정된 라운드의 후속 요청은 저장된 동일 결과 반환
- HP 피해 중복 적용 금지
- 다음 라운드 중복 생성 금지
- 최종 결과 중복 저장 금지

첫 번째 행동 제출은 secret만 갱신한다.

두 번째 행동 제출 트랜잭션은 공개 battle 상태와 secret 상태를 읽고, 현재 `battleId + round`가 아직 판정되지 않은 경우에만 resolve한다.

### 5.6 deadline과 timeout resolve

```text
양쪽 행동 제출 완료
→ 두 번째 제출 요청 안에서 즉시 판정

deadline 도달
→ 참가자 명령 또는 상태 복구 요청
→ 서버 시각으로 deadline 검증
→ 아직 판정되지 않은 현재 라운드만 resolve
```

만료 확인은 다음 요청에서 수행한다.

- 행동 제출
- 배틀 상태 복구
- 재접속
- 포기
- 다음 배틀 명령 처리
- 명시적 `resolve-timeout`

시간 초과 행동은 다음으로 고정한다.

```text
no_action
→ 상대에게 피해를 주지 않음
→ 상대 행동에는 정상적으로 피격
```

같은 참가자가 연속 2회 시간 초과하면 패배한다.

장시간 이탈 후 복구하더라도 여러 만료 라운드를 연속으로 fast-forward하지 않는다.

```text
재접속
→ 현재 라운드만 한 번 timeout 판정
→ 다음 라운드 deadline을 resolve 시점부터 새로 시작
→ 사용자에게 새 선택 기회 제공
```

양쪽 모두 이탈하면 deadline 직후 능동 판정되지 않을 수 있다. MVP에서는 이를 허용한다.

```text
양쪽 이탈
→ 진행 정지
→ 재접속 또는 다음 요청에서 현재 라운드만 처리
→ 장기간 방치된 방은 cancelled 또는 expired 처리
```

상시 라운드 스케줄러나 초 단위 Firestore write 타이머를 추가하지 않는다.

### 5.7 전투 스냅샷

양쪽 참가자가 준비를 마치고 전투를 시작할 때, 서버가 같은 기준 시각으로 공식 슬롯을 투영하고 참가 디지몬 상태를 고정한다.

최소 스냅샷 후보:

```js
{
  uid,
  slotId,
  version,
  digimonId,
  digimonInstanceId,
  combatRevision,
  stage,
  attribute,
  sourcePower,
  powerBreakdown,
  maxHp,
  baseAttack,
  capturedAt
}
```

`sourcePower`는 클라이언트가 제출하지 않는다. 서버가 공식 슬롯의 lazy projection과 기존 `calculatePower()` 경계를 사용해 계산한다.

전투 시작 후 원본 슬롯이 진화·사망하거나 스탯이 바뀌어도 진행 중 배틀 스냅샷에는 반영하지 않는다.

배틀 중 현재 HP와 라운드 상태를 원본 슬롯에 저장하지 않는다.

## 6. 확정된 공통 전투 규칙

아래 규칙은 이번 다섯 후보를 비교할 때 공통으로 사용한다.

### 6.1 전투 형식

```text
1대1
동시 선택형 라운드
최대 7라운드
선택 시간 7초
목표 경기 시간 30초~90초
```

최대 라운드와 선택 시간은 이번 비교의 고정 입력이다. 모든 후보가 목표 경기 시간을 심각하게 벗어나는 경우에만 수치 근거와 함께 blocker로 보고하며, 별도 시간 시스템을 설계하지 않는다.

### 6.2 종료 조건

```text
HP 0 이하
→ KO

양쪽 HP 0 이하
→ 무승부

최대 라운드 종료
→ 남은 HP 비율 비교

남은 HP 비율 동일
→ 무승부
```

### 6.3 속성

```text
Vaccine > Virus
Virus > Data
Data > Vaccine
```

유리한 공격자:

```text
attributeAttack = 1
```

불리하거나 같은 속성:

```text
attributeAttack = 0
```

별도 감점 `-1`은 없다.

`Free`는 누구에게도 유리하지 않고 누구에게도 불리하지 않다.

### 6.4 행동 사용 제한

- 공격 횟수 제한 없음
- 방어 횟수 제한 없음
- 특수공격 횟수 제한 없음
- 특수공격 연속 사용 제한 없음
- 쿨다운·충전·전투당 1회 상태 없음
- 선택한 라운드에서 즉시 판정

특정 반복 행동이 지배 전략으로 확인되면 단순히 제한 상태를 추가하지 말고, 먼저 피해 수치 또는 행동 판정표 자체의 문제인지 보고한다.

## 7. 공통 피해 구조

### 7.1 일반 공격

```text
normalAttackDamage
= baseAttack
+ powerGapAttack
+ attributeAttack
```

수식 표현:

```js
const normalAttackDamage =
  baseAttack +
  powerGapAttack +
  attributeAttack;
```

### 7.2 power 차이 추가 어택

공격자가 강한 경우에만 추가 어택을 얻는다.

```js
const positivePowerGap = Math.max(
  attackerPower - defenderPower,
  0
);

const powerGapAttack = Math.floor(
  Math.sqrt(
    positivePowerGap /
    powerGapUnit
  )
);
```

낮은 쪽의 공격력을 깎지 않는다.

명시적인 보너스 상한은 이번 후보의 기본값으로 두지 않되, 허용된 `sourcePower` 범위와 미래 데이터 이상값에 대한 서버 검증 필요성을 별도로 평가한다.

### 7.3 특수공격

특수공격의 핵심은 고화력이 아니라 방어 관통이다.

```js
const specialAttackDamage =
  normalAttackDamage +
  specialAttackBonus;
```

`specialAttackBonus`는 이번 분석에서 비교한다.

### 7.4 방어 관통

일반 공격 대 방어:

```text
양쪽 피해 0
```

특수공격 대 방어:

```js
const guardPenetrationDamage = Math.ceil(
  specialAttackDamage / 2
);
```

방어 관통 수식 `/2`는 이번 다섯 비교의 공통 입력이다. 다른 관통 시스템을 추가로 설계하지 않는다.

## 8. 행동 판정표

아래 판정표를 고정하고, `공격 vs 특수공격`의 약화 피해만 후보별로 비교한다.

| A 행동 | B 행동 | A가 받는 피해 | B가 받는 피해 |
|---|---|---:|---:|
| 공격 | 공격 | B의 일반 공격 | A의 일반 공격 |
| 공격 | 방어 | 0 | 0 |
| 공격 | 특수공격 | B의 약화 특수공격 | A의 일반 공격 |
| 방어 | 방어 | 0 | 0 |
| 방어 | 특수공격 | B의 방어 관통 피해 | 0 |
| 특수공격 | 특수공격 | B의 특수공격 | A의 특수공격 |

역할 설명:

```text
방어는 공격을 막는다.
특수공격은 방어를 관통한다.
공격은 특수공격과의 교환에서 유리하다.
```

완전한 가위바위보처럼 패배 행동을 반드시 0 피해로 만들지는 않는다. 그러나 어떤 행동도 모든 상대 행동과 전투 상태에서 항상 같거나 좋은 지배 행동이 되어서는 안 된다.

## 9. 비교 후보 1: 공격 대 특수공격 약화 피해

공격 사용자는 일반 공격 피해를 정상 적용한다.

특수공격 사용자가 공격 사용자에게 주는 약화 피해는 다음 네 후보를 비교한다.

### R1. 고정 피해 1

```js
const reducedSpecialDamage = 1;
```

### R2. 원래 특수공격의 25%

```js
const reducedSpecialDamage = Math.ceil(
  specialAttackDamage * 0.25
);
```

### R3. 원래 특수공격의 33%

```js
const reducedSpecialDamage = Math.ceil(
  specialAttackDamage / 3
);
```

### R4. 특수공격 보너스 제거

```js
const reducedSpecialDamage = normalAttackDamage;
```

다음 질문에 수치로 답한다.

- 공격이 특수공격보다 실제로 유리한가?
- 특수공격이 완전히 무효화되지는 않는가?
- 약화 피해가 `sourcePower`, 속성, 단계 차이를 지나치게 무시하는가?
- 약화 피해가 너무 커 공격과 특수공격의 차이가 사라지는가?
- 한 문장으로 플레이어에게 설명 가능한가?

## 14. 전략 시뮬레이션 요구사항

단순 피해 분포만으로 결론 내리지 않는다. 전투 상태와 상대 전략에 따라 행동 가치가 달라지는지 확인한다.

### 14.1 반드시 구분할 전투 상태

```text
HP 동일
내가 HP 비율 25%p 우세
내가 HP 비율 25%p 열세
최종 라운드에서 HP 비율 우세
최종 라운드에서 HP 비율 동률
최종 라운드에서 HP 비율 열세
```

단계별 최대 HP 때문에 정확히 25%p를 만들 수 없으면 가장 가까운 정수 HP를 사용하고 실제 비율 차이를 보고한다. 추가로 일반 공격 1회 피해 차이에서도 결론이 유지되는지 민감도 분석한다.

### 14.2 반드시 비교할 고정 전략

```text
공격 반복
방어 반복
특수공격 반복
```

### 14.3 반드시 비교할 단순 혼합 전략

최소한 다음 정책을 비교한다.

```text
균형형
→ 공격 1/3, 방어 1/3, 특수공격 1/3

공격 중심
→ 공격 60%, 방어 20%, 특수공격 20%

방어 중심
→ 공격 20%, 방어 60%, 특수공격 20%

특수공격 중심
→ 공격 20%, 방어 20%, 특수공격 60%

공격·방어 교대
→ 공격 → 방어 반복

공격·특수공격 교대
→ 공격 → 특수공격 반복

방어·특수공격 교대
→ 방어 → 특수공격 반복

세 행동 순환
→ 공격 → 방어 → 특수공격 반복
```

가능하면 정확한 상태 전이 계산을 사용한다. 경우의 수 때문에 표본 시뮬레이션이 필요하면 고정 seed, 반복 횟수, 오차 범위를 공개해 재현 가능하게 만든다.

### 14.4 지배 행동 판정

어떤 행동 A가 모든 상대 행동과 분석 상태에서 행동 B보다 결과가 나쁘지 않고, 하나 이상의 경우에서 더 좋다면 A가 B를 약하게 지배한다고 본다.

한 라운드의 3×3 payoff matrix와 최대 7라운드 반복 경기 결과를 모두 확인한다. 모든 경우에서 더 좋은 강한 지배와, 모든 경우에서 나쁘지 않고 일부에서 더 좋은 약한 지배를 구분한다.

확인할 내용:

- 공격이 지나치게 안전한 기본 선택인가?
- 공격이 방어를 약하게 지배하는가?
- 특수공격 반복이 방어 관통과 보너스를 동시에 얻어 지배 행동이 되는가?
- HP 우세 측이 방어 반복으로 판정승을 굳힐 수 있는가?
- HP 열세 측에 특수공격 반복 외 선택지가 남는가?
- 혼합 전략이 실제 승률·남은 HP·무승부율을 개선하는가?
- 최종 라운드에서 특정 행동이 사실상 강제되는가?

지배 행동이 발견되면 사용 횟수 제한부터 추가하지 않는다. 어떤 수치 또는 판정 조합이 지배를 만들었는지 분리해 보고하고, 다섯 비교 항목 안에서 해결 가능한지 판단한다.

### 14.5 전략 결과 지표

각 후보 조합에서 최소한 다음을 보고한다.

- 승률
- 패배율
- 무승부율
- 평균 종료 라운드
- 중앙 종료 라운드
- p90 종료 라운드
- KO 종료 비율
- 최대 라운드 판정 비율
- 평균 남은 HP와 HP 비율
- 행동별 선택 가치 또는 기대 HP 교환
- 한 방 KO 및 2회 KO 빈도
- 방어 반복으로 피해 없이 소모된 라운드 비율

동일 단계에서는 허용 데이터의 각 `(version, digimonId)` 조합을 양쪽 방향으로 비교한다. M2에서는 낮은 단계 대 높은 단계의 방향성 조합도 별도로 집계해 전체 평균이 단계 불공정을 가리지 않게 한다.

## 15. 후보 조합 실행 순서

모든 조합을 무작정 같은 깊이로 분석하지 말고 다음 순서로 진행한다.

### 15.1 1차 수치 필터

다음 조합을 계산한다.

```text
HP·baseAttack: H1, H2
특수공격 보너스: S0, S1, S2
공격 대 특수공격 약화: R1, R2, R3, R4
powerGapUnit: P10, P20, P25, P50
매칭 범위: M1, M2
```

기본 교차 곱은 다음과 같이 총 192개 규칙 조합이다.

```text
R 4 × S 3 × H 2 × P 4 × M 2 = 192
```

가능한 한 192개를 전수 계산한다. 계산량 때문에 일부를 생략해야 한다면 생략 기준과 미분석 조합 수를 명시한다.

1차에서 다음 문제를 가진 조합을 표시한다.

- full HP 한 방 KO 빈도가 높음
- 동일 단계에서 대부분 2라운드 이내 종료
- 대부분 최대 라운드까지 피해가 거의 없음
- 높은 단계 또는 높은 power가 사실상 자동 승리
- 특정 행동이 명백한 상위 호환

### 15.2 2차 전략 분석

1차에서 살아남은 조합과 각 후보군을 대표하는 경계 조합을 대상으로 14절의 상태별·혼합 전략 분석을 수행한다.

초기에 제외한 후보도 제외 이유와 핵심 수치를 결과표에 남긴다.

### 15.3 민감도 분석

최종 추천 조합에 대해 다음 값이 한 단계 변했을 때 결론이 뒤집히는지 확인한다.

- HP ±1
- `baseAttack` ±1
- `specialAttackBonus` ±1
- `powerGapUnit` 인접 후보
- 속성 보너스 존재·부재

속성 규칙 자체를 변경하지는 않는다. 속성 +1이 최종 추천의 안정성에 미치는 영향만 본다.

## 16. 코드 조사 요구사항

파일과 라인 근거를 사용해 다음을 확인한다.

### 16.1 데이터 원본

- Ver.1~Ver.5 디지몬 데이터 위치
- 실제 성장 단계 키
- `basePower`와 속성 위치
- 중복 ID와 버전 식별 방식
- `power=0`, `type=null` 같은 보조·이상 데이터
- 현재 아레나 참가 가능 단계 판정

전투 개체의 통계 단위는 `(version, digimonId)`로 정의한다. 같은 `digimonId`가 여러 버전에 있거나 데이터에 중복 등장하면 중복 제거 여부와 근거를 보고한다. 알·유년기·사망 상태와 `power=0`, `type=null`인 보조 helper 데이터는 경쟁 분석에서 제외하고 정확한 제외 건수를 보고한다.

### 16.2 sourcePower 경계

- 기존 `calculatePower()` 구현
- 서버 bundle 또는 서버 parity 경계
- Strength·Traited Egg·Effort 계산
- lazy projection 적용 시점
- 클라이언트 계산값을 신뢰하지 않는 기존 서버 패턴

### 16.3 규칙 격리

새 규칙은 기존 Ghost Arena 계산기와 다른 도메인임을 전제로 한다.

보고서에서 다음을 구분한다.

```text
재사용 가능한 코드
→ 인증
→ 슬롯 서버 projection
→ calculatePower
→ 트랜잭션·멱등 패턴

분리해야 하는 코드
→ 기존 Ghost Arena 판정 수식
→ 기존 +5/-5 속성 함수
→ 클라이언트 직접 write 방 구조
```

구현은 하지 않는다.

### A. 분석 기준선

- 브랜치와 HEAD
- 작업 트리 초기 상태
- 사용한 데이터 원본
- 접근하지 않은 운영 데이터
- 실제 슬롯 표본 존재 여부
- 일회성 분석 방법과 재현 명령

### B. 코드 기준 사실 확인

- 관련 파일과 라인
- 성장 단계·속성·power 데이터 구조
- `calculatePower()`의 실제 의미
- 서버 projection 재사용 가능성
- 기존 Ghost Arena와 분리해야 할 경계

### C. 데이터 통계

- 단계별 디지몬 수
- 단계별 정적 `basePower` 분포
- 속성 분포
- 동일 단계·인접 단계 power gap
- 이상값·누락값·보조 데이터
- 실제 표본과 이론 시나리오 구분

### D. 후보별 수치 결과

각 후보에 대해 다음 형식을 사용한다.

```text
후보별 수치 결과
→ 장점
→ 문제점
→ 추천안
→ 추천 이유
```

- R1~R4 공격 대 특수공격 약화 피해

### E. 전략 시뮬레이션

- 동일 HP

- HP 열세
- 최종 라운드
- 공격 반복
- 방어 반복
- 특수공격 반복
- 단순 혼합 전략

- HP 우세 측 방어 반복 시간 끌기
- HP 열세 측 선택지

각 추천값에 수치 근거와 알려진 한계를 붙인다.

### G. 재현 가능한 테스트 벡터

구현 PR에서 그대로 단위 테스트로 옮길 수 있는 입력·기대 결과를 작성한다.

아키텍처 재검토를 최종 판정으로 사용하지 않는다.

## 18. 금지 작업

이번 요청에서는 다음을 하지 않는다.

- 프로덕션 코드 수정
- 테스트 코드 추가·수정
- 신규 API 구현
- Firestore 컬렉션 생성
- Firestore Rules 수정
- Firestore 인덱스 추가·삭제
- 디지몬 데이터 수정
- `power` 값 보정
- 성장 단계 키 변경
- 기존 Ghost Arena 공식 변경
- 신규 패키지 설치
- `package.json`·lockfile 변경
- 환경변수 추가
- 브랜치 생성
- commit·push·PR 생성
- 배포
- 운영 Firebase·Supabase·Ably 접근
- 실제 데이터 write 또는 migration
- 저장소 안에 영구 분석 스크립트 추가

일회성 분석이 필요하면 다음 조건을 지킨다.

1. 기존 Node 실행 환경과 테스트 helper를 우선 재사용한다.
2. 가능하면 셸 또는 `/tmp` 임시 파일을 사용한다.
3. 저장소 안에 임시 파일을 만들었다면 최종 답변 전에 삭제한다.
4. 분석 스크립트는 운영 서비스에 연결하지 않는다.
5. 작업 종료 시 `git status`와 `git diff --stat`을 확인한다.
6. 기존 사용자 변경사항이나 untracked 파일을 삭제·덮어쓰지 않는다.

## 19. 최종 분석 범위 확정

아키텍처와 서버 계약은 이미 확정됐다.
이번 분석에서는 이를 재논의하거나 다른 기술 구성을 제안하지 않는다.

다음 다섯 항목만 비교한다.

1. 공격 vs 특수공격의 약화 피해
2. 특수공격 기본 보너스
3. 성장 단계별 HP·`baseAttack` 후보
4. `powerGapUnit`
5. 동일 단계 매칭 범위

운영 Firestore, Supabase, Ably 및 기타 운영 서비스 데이터에는 접근하지 않는다.

분석에는 다음 자료만 사용한다.

- 저장소의 정적 디지몬 데이터
- 기존 테스트 fixture
- Firebase Emulator 데이터
- 사용자가 제공한 익명화 export
- `calculatePower()` 코드로 확인 가능한 이론적 범위

실제 육성 슬롯 표본이 없으면 실측 분포를 추정하거나 꾸며내지 않는다.
이 경우 정적 데이터 결과, 이론적 범위, 가상 시나리오를 각각 구분하고 실제 슬롯 분포를 확인할 수 없었다는 한계를 명시한다.

전략 검증은 다음 상태를 포함한다.

- 동일 HP
- HP 우세
- HP 열세
- 최종 라운드
- 공격 반복
- 방어 반복
- 특수공격 반복
- 단순 혼합 전략
- 특정 행동의 약한 지배·강한 지배 여부
- HP 우세 측의 방어 반복에 의한 시간 끌기 가능성

각 후보는 반드시 동일한 형식으로 보고한다.

1. 후보 수치
2. 시뮬레이션 결과
3. 장점
4. 문제점
5. 추천 여부
6. 추천 또는 제외 이유
7. 실제 표본 부족 등 확인할 수 없는 한계

최종 답변은 다섯 항목 각각에 대해 하나의 추천안을 선택한다.
결론을 내릴 근거가 부족하면 임의로 확정하지 말고 추가로 필요한 fixture 또는 익명화 표본을 구체적으로 명시한다.

프로덕션 코드, 테스트, Rules, 인덱스, 설정, lockfile 및 데이터는 수정하지 않는다.
분석 보고서만 작성한다.
